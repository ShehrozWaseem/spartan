Where every merchandise number comes from

This page follows the merchandise money only — t-shirts, medals and gear sold at the races, plus the online store. It shows how the raw file becomes one row per event, how each race is placed in a state when the file never says which state it was in, what tax was collected, and how that compares to what the state's rate says should have been collected.

Season passes are not included anywhere on this page. A pass is not merchandise, so nothing here contains any pass money — no state figure on this page includes pass revenue or pass tax. Passes are also not tied to a race, so they carry no state at all; that is a separate problem, dealt with in the deliverable, not here.

How a race name becomes a state

This is the one judgement call in the whole file, so it is worth understanding. The event tabs name the race but never the state, so the state has to be read out of the name itself. Three rules are applied, in this order.

1. Is it outside the US?
Names matching a country or a known overseas venue are marked international and dropped out of the US figures entirely. events fall out here.
"Spartan Race Korea" → international, excluded
2. Does the name carry a state code?
If the name ends with a two-letter state code after a comma, that wins over everything else. The venue's own address is the best evidence there is.
"Badlands, Attica, IN" → IN
3. Otherwise, match on a keyword
A list of venue and city keywords maps to a state. This is the fallback and the only place a mistake can creep in — regional names like "MidWest" or "Carolinas" are the risky ones.
"Fenway Park" → MA
The bracket rule
Brackets in a race name mean two different things. Sometimes they hold the real venue, sometimes they hold history. Only history is thrown away; a bracket holding the venue is kept and used.
"(Previously Chicago MLS)" → ignored  ·  "(Oaks, PA)" → used
Every one of the events was re-checked against this rule on 28 Sep. Nine were in the wrong state and were moved — see what changed. One event still cannot be placed, and is left unallocated on purpose.

The summary sheets

the rate columns, and what they do and do not prove
Which columns are tax? Only Tax Collected is real money charged to a customer — it is summed from the source file and never calculated. Expected Tax is our own arithmetic (net × the state's base rate) and Gap is the difference between the two. Expected and Gap are a diagnostic to point you at states worth looking at; neither is a figure you would ever file.

What changed on 28 Sep

Two fixes. Neither changes the company total — the same merchandise revenue and the same tax collected are still reported. Only the split between states moved, and columns that were empty now fill.

YearCompanyEventWasNowNet salesTaxWhy it was wrong
The rate columns were also repaired. A column was inserted into the rules matrix on 25 Aug, and the script was still reading the rate by position. From that day it picked up the word "Taxable" instead of a rate, so every Base Rate, Expected Tax and Gap cell came back empty and nobody could see which states were under-collecting. The script now finds the column by its heading, so an inserted column cannot break it again. Revenue and tax collected were never affected by this — only the comparison columns.
